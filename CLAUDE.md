## Rotas de API

| Endpoint | Método | Descrição |
|----------|--------|-----------|
| `/api/apify/scrape` | POST | Scraping de Reels de um perfil. Body: `{ username }` |
| `/api/video/process` | POST | Download + FFmpeg strip + upload Supabase. Body: `{ videoUrl, filename, reelData }` |
| `/api/library` | GET | Lista vídeos da tabela `videos_library` |
| `/api/library` | DELETE | Remove vídeo do Storage e do banco. Body: `{ id, storage_path }` |
| `/api/schedule` | POST | Cria postagens agendadas. Body: `{ video_id, account_ids, caption, scheduled_at }` |
| `/api/schedule` | GET | Lista postagens agendadas com joins |
| `/api/logins` | GET/POST/DELETE | Cofre de credenciais de login (Logins Vault) |
| `/r/[slug]` | GET | **Rota pública** do redirecionador. 302 para o `destination_url` ativo. Sem sessão, sem cache, `noindex` |
| `/api/links` | GET/POST | Lista e cria Links Gerenciáveis |
| `/api/links/[id]` | GET/PATCH/DELETE | Detalhe + histórico, edição (destino/status/vínculos) e exclusão definitiva |
| `/api/links/[id]/analytics` | GET | Agregação de cliques por RPC (`?days=7`, `30` ou `90`) |
| `/api/queue/stats` | GET | Estatísticas da fila de publicação em tempo real |
| `/api/failover/accounts` | GET/PATCH/PUT | Gerenciar health e prioridade de contas para failover |
| `/api/failover/logs` | GET | Histórico de eventos de failover |
| `/api/proxy-download` | GET/HEAD | Proxy de vídeo seguro (streaming puro, allowlist SSRF, iPhone UA) |
| `/api/proxy-download` | GET/HEAD | Download do arquivo ORIGINAL (streaming puro, allowlist SSRF, iPhone UA). A rota `/api/proxy-sanitize-download` foi REMOVIDA em 2026-09-06 — download nunca transforma a mídia |

**Modo mock:** Sem as variáveis de ambiente configuradas, ambas as rotas retornam dados simulados para desenvolvimento local.

## Banco de Dados (Supabase)

### Tabelas

- **`videos_library`** — Vídeos processados e salvos pelo usuário
- **`instagram_accounts`** — Contas do Instagram conectadas
- **`scheduled_posts`** — Postagens agendadas
- **`scraped_profiles`** — Cache de perfis raspados (histórico de Inspirações)

Todas as tabelas têm RLS habilitado. Scripts em `supabase/schema.sql` e `supabase/storage.sql`.

### Storage

- **Bucket:** `videos-library` (público, limite 500 MB por arquivo)
- **Tipos aceitos:** `video/mp4`, `video/quicktime`, `video/webm`

## Decisão arquitetural — Processamento de vídeo opt-in por publicação (2026-09-06)

Regra permanente do projeto. Vale para qualquer fluxo novo.

- **A mídia entra na Biblioteca sem transformação deliberada.** Inspirações, upload manual e Clone salvam o arquivo como ele veio da fonte. Re-hospedar (CDN → Supabase Storage) é permitido; alterar o conteúdo não.
- **O original é imutável.** `videos_library.public_url` sempre aponta para o arquivo original. Nenhum fluxo pode sobrescrever a linha com uma versão processada.
- **O padrão é `original`.** Registros antigos e qualquer valor desconhecido/nulo caem em `original` (`normalizeProcessingMode`). Não existe backfill que force limpeza.
- **A limpeza só acontece quando o usuário escolhe** `clean_metadata` na configuração da publicação. A escolha é persistida no banco e copiada para o post/container concreto — não vive só no estado do React nem é relida da configuração na hora de publicar.
- **`clean_metadata` é stream copy, nunca re-encode.** Proibidos no caminho de limpeza: `libx264`, CRF, `noise`, `hue`, `eq`, `volume`, `atempo`, `setpts`, `unsharp`, `smartblur`, `crop`, `scale`, e injeção de `creation_time`.
- **`clean_metadata` nunca faz fallback automático para `original`.** A escolha de processamento persistida no post é soberana. Se o preparo da variante falhar, a publicação fica bloqueada (post `failed` com motivo, container de erro no Loop, `last_error` no template de Story) — o vídeo original NÃO entra no lugar. Só duas coisas fazem um conteúdo sair como original: o usuário ter escolhido `original` desde o começo, ou o usuário mudar a configuração/post explicitamente. Retry controlado por `video_variants.attempts` (teto de 3); depois disso a variante fica em `error` terminal.
- **Efeitos criativos são outro conceito.** Espelho/zoom/blur/ruído/anti-IA re-encodam por definição, rodam só quando ativados no Loop e usam a fila `video_processing_jobs`. Sem efeito ativo, nenhum re-encode acontece — regra que já custou duas regressões de alcance (18/06 e 08/07/2026).
- **Efeitos criativos não adicionam `creation_time` nem metadata falsa deliberadamente.** Aplicam apenas as transformações que o usuário selecionou. O re-encode gera naturalmente um container novo; `-map_metadata -1` remove o que veio da entrada, mas nenhum campo artificial (data de criação, UUID, hash bust) é inventado.
- **Nunca reintroduzir sanitização ou fingerprint automático no caminho padrão**, em nenhuma origem de postagem.
- **Os crons de publicação devem receber a mídia pronta.** `publish-scheduled` e `process-loops` publicam; quem prepara vídeo é o `process-videos`. Se a variante não estiver pronta, o post espera (`pending`) — nunca falha e nunca roda FFmpeg na hora de publicar.
- **SEI NAL units não são mais removidos.** A hipótese antiga ("SEI = fingerprint secreto da Meta") nunca foi comprovada. O fato de produção era apenas que vídeos upados pelo browser davam `ERROR/EXPIRED` na Meta e passavam a funcionar após o pipeline — que também aplica `+faststart`, e moov atom no fim do arquivo é causa conhecida e documentada de rejeição em consumo por URL remota, explicação que não depende de nenhuma hipótese sobre fingerprint. Como SEI type 6 carrega dados legítimos (closed captions CEA-608/708, metadados HDR/mastering display, timecode, pic_timing), remover às cegas degrada o arquivo sem benefício comprovado. NAL type 5 (IDR keyframes) nunca pode ser removido. Se algum vídeo for rejeitado e o remux com faststart não resolver, o filtro pode voltar como opção explícita — nunca como padrão.

Arquivos-chave: `lib/video-processing.ts` (modo + variantes), `lib/ffmpeg-process.ts` (única função de limpeza), `lib/media-ingest.ts` (download sem transformação), `components/dashboard/VideoProcessingSelector.tsx` (UI), `scripts/test-video-processing.mjs` (verificação).

## Decisão arquitetural — Links Gerenciáveis (2026-09-07)

Regra permanente. Vale para qualquer evolução do módulo de links.

- **Um slug, um destino, para todos.** O redirecionador NUNCA escolhe destino
  por User-Agent, referrer, país, idioma ou "parece um crawler". Não existe
  cloaking, mascaramento para burlar plataforma nem página diferente para bot.
  O User-Agent é lido só para virar categoria de analytics, e o resultado dessa
  leitura jamais entra no cálculo da URL final.
- **Nenhum redirect é controlado por parâmetro de URL.** O destino é
  previamente persistido por usuário autenticado, validado no servidor na
  escrita e na leitura, e resolvido exclusivamente pelo slug. A rota pública
  não aceita `?url=` nem qualquer outro parâmetro que escolha destino, e não
  pode passar a aceitar.
- **O slug é imutável.** Ele já foi divulgado. Editar link significa editar
  destino, nome, status ou vínculos; nunca o slug. Excluir de vez libera o slug
  para reuso, e por isso a ação padrão da UI é **arquivar**, não excluir.
- **302, nunca 301.** O destino é mutável por definição; 301 ficaria cacheado no
  navegador do visitante apontando para o destino velho. Junto vai
  `Cache-Control: private, no-store` — nem CDN nem browser seguram o destino
  anterior — e `X-Robots-Tag: noindex, nofollow`.
- **Um round-trip resolve tudo, nesta ordem:** busca pelo slug → valida
  `status = 'active'` → valida o destino (`is_valid_link_destination`, que
  espelha `validateDestinationUrl` do TypeScript) → **só então** conta o
  clique → devolve o destino. O contador é somado dentro do próprio UPDATE
  (`click_count = click_count + 1`): nunca ler-somar-gravar no TypeScript, que
  perderia cliques concorrentes.
- **`click_count` conta redirect bem-sucedido, e só isso.** Visita a link
  pausado, arquivado, inexistente ou com destino inválido não incrementa nada e
  não vira linha em `managed_link_clicks`. Não existe métrica de "visita
  rejeitada"; se um dia existir, precisa de coluna/tabela própria — nunca
  misturada em `click_count`.
- **Contador e linha de detalhe têm savepoints separados.** São coisas
  diferentes: se o INSERT de detalhe falhar, o redirect aconteceu e o contador
  continua valendo. Consequência aceita: nesse caso `click_count` fica maior
  que `count(*)` de `managed_link_clicks`.
- **`country` é analytics best-effort.** Vem de header de borda
  (`x-vercel-ip-country`), que é falsificável e pode faltar. Entra no INSERT do
  clique e em nenhum outro lugar: nunca em autorização, decisão de segurança,
  escolha de destino ou cloaking.
- **Credencial nunca é serializada para o browser.** Nenhuma rota consumida por
  Client Component pode ter `access_token`, `meta_access_token`,
  `ig_app_secret` ou proxy em texto claro no SELECT. Se a UI precisar saber que
  a credencial existe, exponha um booleano derivado no servidor.
- **Analytics nunca bloqueia o redirect** — e nunca vira `void promise`. Em
  serverless a função congela ao responder e a promise solta morre; por isso o
  registro acontece ANTES da resposta, dentro de um bloco `EXCEPTION` que isola
  a falha. Se o clique não puder ser gravado, o visitante é redirecionado do
  mesmo jeito.
- **Analytics sem dado pessoal.** Nada de IP (nem hasheado), nada de User-Agent
  completo, nada de URL de referer inteira — só hostname, categoria de
  dispositivo, família de navegador, país (2 letras) e UTM. "Cliques únicos"
  ficou fora do MVP justamente porque exigiria derivar identidade do visitante.
- **Toda contagem é agregada no banco.** `managed_link_clicks` cresce sem teto e
  o PostgREST corta em 1000 linhas em silêncio (lição de 2026-08-29). Nenhuma
  tela pagina clique a clique: as RPCs `get_managed_link_overview` e
  `get_managed_link_analytics` devolvem os números já somados.
- **Repasse de parâmetro tem precedência do destino.** Com
  `forward_query_params`, o que já está no `destination_url` vence o que veio na
  URL pública — a query do visitante é controlável por terceiros e não pode
  sobrescrever configuração do dono. Merge sempre por `URLSearchParams`, nunca
  por concatenação de string.
- **O domínio nunca é hardcodado.** `NEXT_PUBLIC_REDIRECT_BASE_URL` é a fonte da
  verdade; sem ela a UI avisa e usa a origem atual.
- **Vínculo com conta e campanha é organização, não posse.** Não muda o redirect
  e não pode virar requisito. Campanha não tem FK porque não existe tabela
  canônica de campanhas neste schema — a validação de dono é feita na API.
- **Story recebe a URL pública, nunca o destino.** O servidor deriva `/r/{slug}`
  a partir do slug; o que o frontend mandar é ignorado quando há link
  gerenciado. É isso que permite trocar o destino depois sem refazer nada. A
  Content Publishing API do Instagram **não aceita link sticker** — a UI diz
  isso explicitamente em vez de fingir que o sticker é anexado sozinho.

Arquivos-chave: `lib/managed-links.ts` (validação, slug, categorias, merge),
`lib/managed-links-db.ts` (ownership de conta/campanha), `lib/link-base-url.ts`
(domínio no client), `app/r/[slug]/route.ts` (rota pública),
`supabase/managed_links.sql` (tabelas, RLS, RPCs),
`scripts/test-managed-links.mjs` (165 checagens).

## Decisão arquitetural — Legenda original de Reels (2026-09-07)

Regra permanente. Vale para qualquer fluxo novo que ingira ou publique Reel.

- **Mídia e legenda são coisas separadas.** Esta feature não altera bytes de
  vídeo, Storage, `video_processing_mode`, FFmpeg, efeitos nem metadata de
  arquivo. É só texto.
- **O scraper preserva a legenda inteira.** Nada de truncar, traduzir, resumir,
  reescrever, remover hashtag/@menção ou trocar emoji na ingestão. Quem corta
  para caber na tela é o CSS, não o banco.
- **Um único lugar interpreta o Apify:** `lib/scraped-reel.ts`. Se um campo
  novo for preciso, ele entra ali — nunca `item.caption || item.text`
  espalhado por rota.
- **Três estados, e a diferença importa:** `null` = legenda não capturada
  (upload manual, ingestão antiga, campo ausente no payload); `""` = o Reel
  não tinha legenda; texto = legenda. `String(x ?? "")` apaga essa distinção e
  por isso não é usado.
- **Vídeo e legenda andam juntos.** A associação é por linha/índice, do item do
  dataset até o post concreto. Nunca existe "a legenda do perfil" nem "a
  legenda do primeiro Reel" aplicada aos demais.
- **Snapshot é obrigatório.** A legenda é resolvida quando o vídeo concreto é
  escolhido e gravada em `scheduled_posts.caption` /
  `pending_containers.caption`. `publish-scheduled` só LÊ esse texto: não
  descobre vídeo, não relê configuração, não chama Apify. Editar o vídeo na
  Biblioteca ou o Loop depois não muda post que já nasceu.
- **Sem fallback silencioso.** `caption_mode=original` com legenda
  indisponível publica SEM legenda. Nunca cai para legenda personalizada,
  automática, de IA ou de outro vídeo. Em publicação individual (Postar agora)
  a UI barra e pede outro modo; em Loop/Postar com pasta mista a UI avisa que
  vídeos sem legenda saem sem legenda.
- **NULL preserva o passado.** `caption_mode` nulo = `custom` = o que o
  fluxo já fazia (pool digitado ou legenda automática). Clone é a exceção
  documentada: o padrão dele é `original`, porque publicar a legenda do Reel
  sempre foi o comportamento daquele fluxo. Nenhum backfill.
- **CAPTION NUNCA É TRUNCADA SILENCIOSAMENTE.** É a regra mais dura desta
  feature. Os três limites da referência oficial da Meta (IG User Media —
  "Maximum 2200 characters, 30 hashtags, and 20 @ tags") são **validados**, e
  legenda fora deles **bloqueia a publicação com erro explícito**. Nada de
  `slice`, `substring`, `truncate` ou remoção automática de hashtag/@menção em
  nenhum ponto do caminho da legenda — nem como "última rede de proteção".
- **Um validador central:** `validateInstagramCaption()` em
  `lib/reel-captions.ts`, com os códigos `CAPTION_TOO_LONG`,
  `CAPTION_TOO_MANY_HASHTAGS` e `CAPTION_TOO_MANY_MENTIONS`. As constantes
  `INSTAGRAM_CAPTION_MAX_LENGTH/HASHTAGS/MENTIONS` são a única fonte desses
  números — não repetir 2200/30/20 em rota, cron ou UI.
- **A validação é do TEXTO FINAL.** A ordem é: resolve o modo → aplica o strip
  de hashtags/@menções, se o usuário ligou → **valida** → snapshot. Validar
  antes do strip reprovaria justamente a legenda que o usuário mandou podar.
- **Vale para `original` e para `custom`.** Legenda digitada não ganha exceção.
  `none` não valida conteúdo (resolve para vazio, e a caption é omitida do
  payload).
- **O transporte tem defesa final.** `assertCaptionValid` roda imediatamente
  antes de montar o payload e lança `InvalidCaptionError`: se um fluxo legado
  gravar legenda inválida, a requisição à Meta não sai. O transporte bloqueia —
  nunca conserta. `sanitizeCaption` só remove bytes nulos, caracteres de
  controle C0 e espaço externo.
- **Comprimento em code points** (`[...text].length`), para emoji contar como 1
  caractere. Não é grapheme cluster (uma família com ZWJ ainda conta como
  vários): escolha consciente, documentada em `captionLength`.
- **Erro não vaza a legenda no log** — só o código e os números.
- **Atribuição não some sozinha.** Hashtags e @menções — inclusive crédito ao
  criador — só são removidas se o usuário ligar o toggle. Default é false nos
  dois, e a remoção usa classes Unicode (`\p{L}\p{N}\p{M}`), não `\w`,
  para não quebrar `#ação` ou `#日本語`.
- **Legenda é conteúdo externo.** Renderizada sempre como texto em JSX. Nunca
  `dangerouslySetInnerHTML`. Quebra de linha vem de `whitespace-pre-wrap`,
  não de HTML.
- **Ownership no servidor.** Buscar `videos_library.caption` sempre com
  `.eq("user_id", user.id)` na mesma query. Em modo `original` o texto vem do
  banco e o que o cliente mandou é ignorado.
- **Stories fora.** A Content Publishing API não usa caption em Story; nenhuma
  lógica desta feature entra nesse fluxo.

`lib/reel-captions.ts` (modos, resolução, limite, Unicode),
`components/dashboard/CaptionModeSelector.tsx` (UI),
`supabase/original_reel_captions.sql` (migration),
